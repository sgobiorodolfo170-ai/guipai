## 0. 一页结论

**评级：C+ / 6.0 分（10 分制）**

| 视角 | 评分 | 说明 |
| --- | --- | --- |
| 作为「单人自用的原型工具」 | **8.0** | 功能完整、数据链路自洽、迭代极快，已经能用 |
| 作为「可交付/可长期维护的产品」 | **5.0** | 零自动化测试、零静态检查、本地服务无鉴权、仓库 875MB |

**三句话总结**：

1. **业务与数据层是这个项目最强的部分**——DB-first + write-on-miss + 多源熔断 + 弃用上游后自研推导（复权因子、连板数、复盘指标），设计成熟度和注释质量明显高于同规模个人项目。
2. **工程护栏是这个项目最弱的部分**——135 个 API、33.5k 行代码、30 个版本，**0 个测试文件、0 个 lint 配置、0 条 CI**；历史事故（v1.7.0 一次编辑事故让整个 Express 起不来）证明纯手工验证已经到极限。
3. **两个必须尽快处理的问题**：本地 HTTP 服务对局域网 + 任意网页开放且无鉴权（P0）；仓库里躺着 296MB 的 `dolphindb.exe` 等 971 个二进制文件，`.git` 已 875MB（P1）。

## 2. 架构与技术选型评估

### 2.1 运行时链路

```
Electron 主进程
├── 拉起 DolphinDB（随包分发，8848）        ← 时序/历史数据仓
├── 拉起 Python 桥（8889，通达信 tqs）      ← 行情上游
└── 内嵌 Express（8080，同进程）
      ├── routes/*（135 端点，只读库为主）
      ├── sources/registry.js（多源调度：failover / race / 熔断 / 超时）
      └── sql.js（内存 SQLite，2s 防抖落盘到 userData）

渲染进程（Vue SPA，hash 路由）
└── axios → http://localhost:8080/api/*
```

### 2.2 选型逐项判断

| 选型 | 判断 | 理由 |
| --- | --- | --- |
| Electron + 内嵌 Express | ✅ 合适 | 单人桌面工具，无需部署、无跨域、可直连本机通达信，是这类需求的最短路径 |
| **sql.js（WASM 内存库）** | ⚠️ 可接受，但有代价 | 免去 native 模块重编译，代价是**全量导出落盘**（2s 防抖）、无 WAL、单文件损坏即全丢。个人交易流水存在这里，建议至少加滚动备份 |
| DolphinDB | ✅ 合理 | 2427 万行日K + 复权推导，列存 + 分区确实省事；代价是 296MB 二进制 + 冷启动 60s |
| 通达信三路 + 腾讯 | ✅ 务实 | 免 Key、免限频、数据质量够用；代价是强依赖本机环境（tdx_quant 需登录客户端） |
| Vue 3 + Element Plus + KLineCharts | ✅ 合适 | 组件齐、K 线库专业，符合 A 股红涨绿跌定制需求 |
| 无 TypeScript | ⚠️ 可接受 | 但 135 个端点靠 `{code,msg,data}` 约定，缺类型即缺契约，是字段映射类缺陷的温床（见 §5） |

**总体判断**：技术选型与「单人 / 桌面 / A股 / 免部署」的约束高度匹配，没有明显过度设计。真正的债务不在选型，而在**持久化可靠性**和**验证手段**。

## 3. 做得好的地方（有据可查）

1. **DB-first + write-on-miss 的数据治理**
   前端只读 sql.js / DolphinDB，上游取数降级为"写路径"（缓存 miss → 读库 → 未命中才联网 → 入库 → 读回）。这是同类项目里很少见到的自觉，直接消灭了"页面等上游超时"的体验问题（v1.8.0 起）。

2. **多源调度器设计成熟**
   `sources/registry.js` 同时具备：逐源超时（按数据类型分档）、连续失败 3 次进 30s 冷却、空结果不误判为失败、failover / race 双策略、失败原因聚合进 message、健康度对外暴露。注释把"为什么这么设计"写清楚了（软封空结果歧义、健康度记忆），这是可维护性的关键。

3. **弃用上游后的自研替代做得彻底**
   连板数（按连续涨停池交易日推导）、复权因子（`stock_adj_factor` + `derive-adjust`）、复盘 7 项指标全链路自研（v1.30.0 提交信息明写"零上游依赖"）。这是把"数据源红线"从口号变成了实现。

4. **变更日志的颗粒度极高**
   30 个版本，每条都写清**根因 → 方案 → 实测数据 → 验证结论**（如"卡片 33 只 vs 池 45+"、"茅台/招行/五粮液交叉验证"）。这在个人项目里非常罕见，是排障时最值钱的资产。

5. **规范落地不是摆设**
   `AGENTS.md` 的"字段变更必须同步 `FIELD_DEFS` + `SQLITE_COVERAGE`"被真实执行：`review_statistics`、`stock_dividend`、`stock_adj_factor`、`trade/position/risk_snapshot` 均已登记，字段由后端驱动渲染（v1.30.0 之后无需逐表改模板）。

6. **DolphinDB 脚本注入防护到位**
   `params.js` 的 `safeSymbol/safeDate` 白名单被引用 90 处；抽查 `adj-factor-repository.js`、`dividend-repository.js`、`holding-repository.js`，均在拼接前先做白名单校验，**不是只在外层路由做**。

7. **前端有错误兜底**
   `ErrorBoundary` 包裹 `router-view` + 全局 `errorHandler` + 未捕获 Promise 上报到 `renderer-error.log`（v1.13.1 修的"间歇性黑屏"），429 用 warning 而非 error 提示。这类细节说明作者踩过坑并沉淀了。

## 4. 风险与问题清单

### P0（建议 1 周内处理）

#### P0-1 本地 HTTP 服务暴露面过大：无鉴权 + 全接口 CORS + 绑定所有网卡

- **证据**：
  - `electron/server/index.js:32` → `app.use(cors({ origin: true, credentials: false }))`（反射任意 Origin）
  - `electron/server/index.js:225` → `app.listen(port, cb)`，**未指定 host**，Node 默认绑定 `::`/`0.0.0.0`
  - 全项目无鉴权中间件（`index.js` 中无 token/session 校验）
- **影响**：
  - 同一局域网内任何设备可直接 `http://<你的IP>:8080/api/cockpit/trades` 读取**持仓、交易流水、笔记、自选股**，并可 POST/DELETE 修改；
  - 用户浏览器里任意网页的 JS 也可向 `http://127.0.0.1:8080` 发起请求（CORS 全放行），属于典型的本地服务被跨站滥用场景；
  - 桌面应用不需要对外提供服务，这是纯粹的攻击面。
- **修复（约 0.5h）**：
  1. `app.listen(port, '127.0.0.1')`；
  2. CORS 改为白名单：开发态 `http://localhost:5174`，生产态允许 `file://`（`Origin: null`）；
  3. 启动时生成随机 token，经 `preload` 注入渲染进程，Express 中间件校验 `X-App-Token`（成本极低，可彻底关死浏览器侧调用）。

#### P0-2 零自动化测试 + 零静态检查，验收只剩"手工点"

- **证据**：全仓无 `*.test.js` / `*.spec.js` / `vitest.config.*` / `.eslintrc*` / `eslint.config.*` / CI 配置；`AGENTS.md` 明确写了"原型阶段以构建+手动运行验证替代"。
- **为什么现在必须补**：
  - 规模已到 **135 个端点 / 33.5k 行 / 21+16 张表**，早已超出"人肉可回归"的范围；
  - 历史事故证明风险是真实的：v1.7.0 一次编辑事故"只留导出语句"导致 `ReferenceError`、**整个 Express 起不来**，且 `node --check` 查不出；
  - 同类缺陷在本项目反复出现（见 §5），靠每次手测同一个坑会反复踩。
- **最小可行方案（2 天，不求覆盖率）**：
  - `node:test`（Node 22 内置，零依赖）覆盖**纯函数与推导逻辑**：复权因子推导、连板数计数、复盘 7 指标、cockpit 盈亏/胜率公式、`safeSymbol/safeDate`；
  - 一个**冒烟脚本**：起服务 → 打 20 个核心端点 → 断言 `code===200` 且字段非空（现有 `electron/server/_e2e_run.js`、`dolphindb/e2e.js` 已有雏形，整理成 `npm run smoke` 即可）；
  - `eslint` 只开 `no-undef` + `no-unused-vars` 两条规则，就能拦住 v1.7.0 那类事故。

#### P1-2 巨石文件，业务逻辑写在路由层

- **证据**：`aktools.js` 1002 行、`market.js` 861、`stock.js` 831、`statistics.js` 752、`cockpit.js` 477；前端 `RandomStockPractice.vue` 1592、`Review.vue` 1111、`KLineChart.vue` 750。

#### P1-3 仓库 875MB，二进制进 Git

- **证据**：`git ls-files` 1172 个文件中 **971 个**来自 `dolphindb-server/`；`dolphindb.exe` **296MB**、`libDolphinDB.dll` 76MB、`libstdc++-6.dll` 20MB；`.git` 875MB，其中松散对象 493MB。
- **影响**：clone / 备份 / 换机成本极高；任何 CI 都会被拖死；`git gc` 也压不下去（对象本身就在历史里）。
- **建议**：`dolphindb-server/` 移出仓库，改为构建时下载或 `electron-builder` 的 `extraResources`；历史清理需 `git filter-repo`（破坏性，需你确认后执行）。

#### P1-4 打包体积与未使用依赖

- **证据**：两个 1.1MB chunk（gzip 372KB + 364KB），Vite 已警告 >500KB；`package.json` 中 `three@0.125.0`、`vanta`、`lodash`、`js-cookie` **在 `src` 中零引用**。
- **影响**：桌面端冷启动首屏（尤其机械盘/低配机）会明显慢；`three` + `vanta` 纯占安装体积。
- **建议**：`build.rollupOptions.output.manualChunks` 拆 `element-plus` / `echarts`；删除 4 个未使用依赖（0.5h）。

#### P1-5 sql.js 单文件持久化，无备份

- **证据**：`db.js:52` `persist()` 全量 `export()` 覆盖写；写入经 `scheduleSave()` **2s 防抖**；`closeDb()` 会补一次 persist（退出安全）；全仓无 `backup`/`copyFile` 逻辑；实际库 `%APPDATA%\guipai\data\tradeinsight.db` 仅 268KB。
- **影响**：正常退出不丢数据（已处理）；但**进程被杀/断电**最多丢 2s 写入（可接受）；真正的风险是**单文件损坏 = 交易流水/持仓/笔记全丢**，且没有历史副本。
- **建议**：每日首次启动时 `copyFile` 一份到 `data/backups/YYYY-MM-DD.db`，保留 7 份；启动时跑 `PRAGMA integrity_check`，失败则提示从备份恢复。**约 1h，收益极高**。

#### P1-6 DolphinDB 强依赖与冷启动

- **证据**：`main.js` 启动时轮询 8848 最多 60s；未就绪则跳过当日补跑（v1.20.1）；`package-sync` 有"DDB 未就绪守卫"。
- **影响**：DDB 起不来时，日K/复盘/板块大面积降级，只有 sql.js 相关页面可用。这是架构性单点，短期难改，但应**在 UI 上明确降级态**（哪个页面因 DDB 不可用而受限），而不是静默空数据。

## 5. 缺陷模式分析（比单条 bug 更重要）

对 30 个版本做归类，**20 个版本含"修复"**，且集中在三个模式：

| 模式 | 出现次数（关键词） | 典型案例 | 根因 |
| --- | --- | --- | --- |
| **字段映射/口径不一致** | "字段" 17 次 | v1.27.1 详情页 `mapSpotRow` 缺 OHLC；v1.27.2 名称被代码覆盖；v1.30.0 卡片 33 vs 池 45 | 同一指标存在多条取数路径（`daily_k` / `daily_k_raw` / `daily_k_qfq` / `stock_spot`），缺"口径字典"与契约测试 |
| **缓存/时序** | "缓存" 18 次 | v1.20.2 指数 overview 与 K 线末根不一致；v1.2.0 空缓存不存导致不自愈 | 缓存 key 与失效策略分散在各路由，无统一层 |
| **路由/顺序/空值** | "路由顺序" 1 次 + 多处 | `DELETE /trades/demo` 被 `/trades/:id` 吞掉；`/review/range` 顺序问题；`Number('demo')=NaN` | Express 路由匹配顺序 + 缺参数校验，属"框架常识型"缺陷，lint/契约测试可拦 |

**结论**：这个项目的缺陷**不在算法层**（复权、连板、盈亏公式这些复杂推导反而写得很扎实），**几乎全部在集成层**——字段名、口径、顺序、缓存。这类缺陷用"跑一次页面"很难覆盖全，但用**契约测试（断言响应字段存在且类型正确）+ 口径字典（每个指标写明唯一权威表）** 能以极低成本消灭大半。
